## 1. Executive Summary & Problem Investigation

Per `prinical.md` (Rule 1 Desktop-first investigation, Rule 3-4 Web vs Desktop comparison, Rule 5 .md approval file, Rule 15 Date Format adherence across all screens/reports/PDFs, Rule 18 Desktop PR rules):
The user requested an investigation into two specific issues:
1. **PDF Date Format Issue (Desktop & Web)**: Generated PDFs still display `DD/MM/YYYY` even when a different date format (e.g. `YYYY-MM-DD`, `DD-MM-YYYY`, `MM/DD/YYYY`) is configured in Company Settings.
2. **Web Email Modal Message Body Height**: In the unified email modal (`Transmit Sales Return Credit Note via Email` and other transactions), the Message Body textarea is constrained to a tiny single/double line box (~40px high), preventing users from viewing the complete multi-line message body without cramped scrolling.

---

## 2. Root Cause Analysis: Why PDF Was Showing `DD/MM/YYYY`

### Root Cause 1: Server `ConfigManager` was strictly ThreadLocal without global business settings
- In `server/src/main/java/org/example/config/ConfigManager.java`, settings were stored in `ThreadLocal<Map<String, String>> VALUES`.
- When `CanonicalDocumentService.renderSalesPdf` executed, it called `TaxInvoicePdfGenerator.generate(...)` **outside** `ConfigManager.withValues(config, ...)`.
- As a result, `TaxInvoicePdfGenerator`'s `formatDate` called `BusinessClock.formatDate(LocalDate)` which called `BusinessClock.datePattern()`.
- Inside `BusinessClock.datePattern()`, `ConfigManager.get("company.dateFormat", "")` returned `""` because the thread-local values were empty.
- It then fell back to `System.getenv("DSE_BUSINESS_DATE_FORMAT")`, which defaulted to `"dd/MM/yyyy"`.

### Root Cause 2: Server-to-Desktop Sync Overwrote Desktop Date Format
- When Desktop booted or connected to Server (`RuntimeBootstrapper.java`), it fetched `/api/runtime/status`.
- `/api/runtime/status` called `BusinessClock.datePattern()` on the server, which returned `"dd/MM/yyyy"`.
- Desktop's `RuntimeBootstrapper` then called `ConfigManager.applyServerBusinessPolicy(status.businessZone(), status.dateFormat(), status.timeFormat())`, which overwrote the desktop's local runtime business date format to `"dd/MM/yyyy"`.

### Root Cause 3: Precedence and Key Inconsistency (`date.format` vs `company.dateFormat`)
- In `CanonicalDocumentDataFactory.java` line 685:
  `String pattern = cfg(c, "date.format", cfg(c, "company.dateFormat", "dd/MM/yyyy"));`
- The legacy key `"date.format"` was checked *before* `"company.dateFormat"`. The settings UI saves to `"company.dateFormat"`. If `"date.format"` existed in the database, it permanently shadowed the user's setting.
- Furthermore, `pattern` was not normalized with `BusinessClock.normalizeDatePattern(pattern)`. If uppercase patterns like `"YYYY-MM-DD"` were passed, Java's `DateTimeFormatter` threw an `IllegalArgumentException` (because `Y` is week-based year), causing it to fall back to `"dd/MM/yyyy"`.

### Root Cause 4: Raw Unformatted Dates in Professional Document Renderer
- In `CanonicalDocumentDataFactory.java`, methods `professionalQuotation`, `professionalReturn`, and `professionalSale` called `rawDate(...)` instead of `date(..., config)`.
- In `ProfessionalDocumentRenderer.java` (in both server and desktop), lines 501, 503, 513, 514, 521, 522, 523, 525, 526 and table cards (lines 699, 700, 711, 777, 781) directly output `data.date`, `data.dueDate`, `data.originalDate`, `data.poDate` as raw strings without calling `displayDate(...)`.
- `ProfessionalDocumentRenderer.displayDate` used `LocalDate.parse(value.substring(0, 10))` which threw an exception whenever the string was not standard ISO `YYYY-MM-DD`.

### Root Cause 5: Web Email Modal Textarea Height Squashed by `.form-input` CSS
- In `css/app.css` line 458-461:
  `.form-input, .form-select { width: 100%; height: 40px; ... }`
- Because `<textarea id="mei-body" class="form-input" rows="5">` had class `form-input`, CSS enforced `height: 40px;`!
- This squashed the multi-paragraph message body into a cramped 40px high field, showing only the greeting line (`Dear Shailesh Dhameliya,`).

## 3. Desktop vs. Current Web Parity Audit (Actual vs. Expected)

| Dimension | Current Actual Behavior | Expected Behavior (v10.0.41 / v10.0.41.01) |
|---|---|---|
| **Tax Invoice PDF Date Format** | Shows `DD/MM/YYYY` regardless of Company Settings. | Dynamically applies Company Settings date format (`YYYY-MM-DD`, `DD-MM-YYYY`, `MM/DD/YYYY`, `dd/MM/yyyy`, etc.) on all invoice dates & PO dates. |
| **Quotation PDF Date Format** | Shows raw unformatted or `DD/MM/YYYY` date. | Dynamically applies Company Settings date format on Quotation Date and Valid Until date. |
| **Returns / Credit & Debit Note PDF Date Format** | Shows raw or `DD/MM/YYYY` date. | Dynamically applies Company Settings date format on Return Date and Original Invoice Date. |
| **Purchase Inward Bill PDF Date Format** | Shows raw or `DD/MM/YYYY` date. | Dynamically applies Company Settings date format on Purchase Date, Invoice Date and Due Date. |
| **Server Runtime Status (`/api/runtime/status`)** | Returned hardcoded fallback `"dd/MM/yyyy"`. | Returns active date format loaded from `application_setting` (`company.dateFormat`). |
| **Web Email Modal Message Body** | Textarea squashed to 40px height (`height: 40px;` from `.form-input`). Only 1 line visible. | Textarea expands to generous height (`min-height: 140px; height: 160px;`), comfortably displaying the entire greeting, adjustment body, and sign-off without cramped scrolling. |

## 4. Implementation Plan & Scope

### Phase 1: Server & Desktop Date Engine Parity (Desktop v10.0.41)
1. **`server/src/main/java/org/example/config/ConfigManager.java`**:
   - Add persistent global settings cache `GLOBAL_SETTINGS` alongside ThreadLocal `VALUES`.
   - Implement `setGlobal(key, value)` and fallback in `get(key, fallback)`.
2. **`server/src/main/java/org/example/server/support/SupportService.java`**:
   - In `@PostConstruct` / startup, seed `ConfigManager.GLOBAL_SETTINGS` from `application_setting`.
   - In `setSetting(key, value)`, update `ConfigManager.setGlobal(key, value)`.
3. **`server/src/main/java/org/example/server/util/BusinessClock.java`**:
   - Update `datePattern()` to prioritize `company.dateFormat` over `date.format`.
   - Enhance `formatDate(String)` to parse ISO, `d/M/uuuu`, `dd/MM/uuuu`, `dd-MM-uuuu`, and `MM/dd/uuuu`.
4. **`server/src/main/java/org/example/server/documents/CanonicalDocumentService.java`**:
   - Wrap `TaxInvoicePdfGenerator.generate(...)` inside `ConfigManager.withValues(config, () -> ...)`.
   - Ensure all render pipelines execute within `ConfigManager.withValues(config, ...)`.
5. **`server/src/main/java/org/example/server/documents/CanonicalDocumentDataFactory.java`**:
   - Prioritize `company.dateFormat` before `date.format` in `date(...)`.
   - Normalize pattern with `BusinessClock.normalizeDatePattern(pattern)`.
   - In `professionalQuotation`, `professionalReturn`, and `professionalSale`, use `date(value, config)` instead of `rawDate(...)`.
6. **`ProfessionalDocumentRenderer.java` (Server & Desktop)**:
   - Ensure all date fields (`data.date`, `data.dueDate`, `data.poDate`, `data.originalDate`) are wrapped in `displayDate(...)`.
   - Upgrade `displayDate(...)` to parse diverse date patterns safely.
7. **`desktop/src/main/java/org/example/util/BusinessClock.java` & `TemplateDataFactory.java`**:
   - Prioritize `company.dateFormat` and support diverse date patterns.

### Phase 2: Web Email Modal & Version Updates (Web v10.0.41.01)
