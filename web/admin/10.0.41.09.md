# Web Studio v10.0.41.09 Specification & Architecture Plan

## 1. Executive Summary & Problem Scope

This specification document outlines the root-cause analysis, desktop ERP parity inspection, architectural plan, and implementation roadmap for **Release v10.0.41.09** of the Jasvi Industries Web Studio, in strict accordance with the rules established in `prinical.md` and `MANDATORY_DEVELOPMENT_PROTOCOL.md`.

### Core Scope Items
1. **KPI Card Uniformity Across All Screens:**
   - Eliminate before vs. after refresh visual discrepancy (flat boxes vs. compact colorful ribbon cards).
   - Eliminate empty right-side blank space on wide screens across all register views.
   - Upgrade Dashboard and Sales Register from legacy 76px `.dash-kpi-card` to match Master Data 58px `.compact-kpi-card` golden standard.
2. **Centralized Dynamic Table Layout & Viewport Auto-Adjustment Audit:**
   - Audit all 42 screens / 34 views containing tables.
   - Identify tables that currently follow vs. do not follow centralized dynamic auto-adjust rules.
   - Resolve header clipping, forced horizontal scrollbars, unconstrained vertical overflow, and failure to adjust when sidebar or side drawers toggle.
3. **Seven (7) Additional Functional Defect Fixes:**
   - Top Header WhatsApp & Email notification badges count not updating / not clearing to zero when read.
   - Recon Supplier screen missing standard 2-row filter toolbar (Search, Date From/To, Quick Presets, Reset, Refresh).
   - Purchase Recon filter toolbar redesign to match standard enterprise 2-row layout.
   - Convert Purchase Recon & Recon Supplier side drawers into centered window modal popups.
   - Fix "New Purchase Recon" save bug where newly created record is not added to the register.
   - Fix Settings screen displaying completely blank when navigated from left sidebar sub-menus.
   - Fix Purchase Creation document attachment widget (+ Add / Replace, Preview, Delete) to match Quotation parity.

## 2. KPI Ribbon Root Cause Analysis & Architectural Design

### Cause 1: Asynchronous Race Condition & Enhancer Lockout on Page Refresh
- In `js/app.js:288`, `GlobalUiEnhancer.init()` runs synchronously during initial boot and calls `runEnhancements(document.body)`.
- This immediately sets the module-level lock `isEnhancing = true`, which is locked for at least 150ms via a `setTimeout` in the `finally` block (`GlobalUiEnhancer.js:44-52`).
- Concurrently, `NavigationRouter.init()` asynchronously fetches the view via `await ViewLoader.loadView()`.
- When `views/purchase-register.html` finishes loading, `ViewLoader.mountView()` calls `GlobalUiEnhancer.enhance(target)`.
- Because `isEnhancing` is still `true`, `runEnhancements(container)` hits line 18:
  ```javascript
  if (isEnhancing) return;
  ```
  and **immediately aborts** without performing any enhancement!
- As a result, on browser refresh, `TableUiEnhancer`, `KpiCardEnhancer`, and `DynamicTableLayoutManager` are completely locked out, leaving the view stuck in its unenhanced raw HTML state.

### Cause 2: Runtime JavaScript DOM Demolition vs. Static HTML Divergence
- When a user later navigates to a screen by clicking a tab, `isEnhancing` is `false`.
- `KpiCardEnhancer.enhanceCard()` executes, destroys `card.innerHTML`, and rewrites the DOM into the compact layout (`.kpi-icon-bubble`, `.kpi-content-box`, `.kpi-row-top`, `.kpi-val-text`).
- Because the raw HTML file contains the old `.kpi-card` markup while the dynamic JS generates `.compact-kpi-card`, the page flips between two entirely different visual representations.

### Cause 3: Golden Standard — Why Master Data (`views/masters.html`) Works 100% Reliably
- Inspection of `views/masters.html` (lines 61–100) reveals the golden standard:
  ```html
  <div class="compact-kpi-ribbon erp-kpi-single-row kpi-grid"
    style="display: flex; flex-direction: row; flex-wrap: nowrap; gap: 8px; margin-bottom: 14px; width: 100%; box-sizing: border-box; overflow: hidden;">
    <div class="compact-kpi-card theme-amber" data-erp-kpi-compact-enhanced="true" style="flex: 1 1 0; min-width: 0; height: 58px; min-height: 58px; max-height: 58px; box-sizing: border-box;">
      <div class="kpi-icon-bubble">📁</div>
      <div class="kpi-content-box" style="flex:1;min-width:0;display:flex;flex-direction:column;justify-content:center;overflow:hidden;">
        <div class="kpi-row-top" style="display:flex;justify-content:space-between;align-items:center;line-height:1;margin-bottom:3px;gap:4px;">
          <span class="kpi-title-text" title="CATEGORIES">CATEGORIES</span>
          <span class="kpi-pill-badge">Groups</span>
        </div>
        <div class="kpi-val-text" id="master-kpi-categories">0</div>
      </div>
    </div>
    ...
  ```
- **Key Success Factors in Master Data:**
  1. The HTML is **natively pre-rendered** in the exact 58px compact ribbon format on Frame 0.
  2. `data-erp-kpi-compact-enhanced="true"` is already set, so JavaScript never destructively rewrites the DOM.
  3. Every card has `flex: 1 1 0; min-width: 0; height: 58px;`, and the container has `width: 100%; display: flex; flex-wrap: nowrap;`.
  4. It stretches seamlessly across the entire width of the screen with zero blank space on the right, and looks identical on cold boot, tab navigation, and refresh.

## 3. Centralized Dynamic Table Layout Audit & Architecture

### Centralized Table Standard (The 3 Mandatory Pillars)
1. **Container Viewport Discipline (`fixed-viewport`):**
   - The root `.module-view` MUST have class `fixed-viewport` (or `.main-content-stage` has `.has-fixed-viewport`).
   - The table MUST be housed in `.sales-table-card` > `.sales-table-scroll` (or `.erp-table-scroll`) with `flex: 1 1 auto; min-height: 0; overflow-y: auto !important; overflow-x: hidden !important;`.
   - Result: Screen height stays locked to viewport (100vh - header - tabs); table header stays sticky; table body scrolls smoothly without expanding whole screen.
2. **Dynamic Column Width Authority (`DynamicTableLayoutManager`):**
   - The table MUST have class `sales-desktop-table` with `table-layout: fixed; width: 100%; border-collapse: collapse;`.
   - `DynamicTableLayoutManager` computes `headerMinimum()` for each token (ensuring header words never clip), applies proportional `flexWeight()` (sponge columns absorb extra space), and injects `<colgroup><col>` elements with percentage widths.
   - On narrow viewports or when side inspection panels open, `allocateDense()` proportionally contracts columns down to dense floors without clipping Action buttons or checkboxes.
3. **Reactive Reflow Authority on Sidebar & Drawer Events:**
   - Whenever the sidebar opens, collapses, or hovers (`aside.app-sidebar.collapsed` / `.hover-peek`), or when a drawer slides in, `DynamicTableLayoutManager.reflowAllTables()` MUST be invoked.

## 4. Root Cause & Solution Design for Seven (7) User-Reported Defects

### Defect 1: Top Dashboard WhatsApp & Email Notification Badges Not Updating / Not Clearing to Zero
- **Root Cause:**
  1. In `js/app.js:239-242`, `applyShellCountsToDom()` displays `counts.whatsapp`, but lacks any read-acknowledgement check (`dse_whatsapp_read_ack`), unlike `counts.email`.
  2. In `CommunicationController.js:30-48`, `loadCommunications()` only clears the email badge (`clearEmailBadge()`), completely omitting WhatsApp.
  3. Every 30 seconds, `pollShellCounts()` queries `/api/insights/shell-counts` and forcefully overwrites `#badge-whatsapp` back to non-zero.
  4. In `NotificationCenterController.js`, opening the notification modal or viewing notifications never marks them as acknowledged in the shell header counter.
- **Architectural Solution:**
  1. Add `dse_whatsapp_read_ack` tracking to `localStorage`.
  2. In `CommunicationController.js`, replace `clearEmailBadge()` with `clearCommunicationBadges()`:
     - Clear `#badge-email` and `#badge-whatsapp` in DOM.
     - Add class `zero` to both counter badges.
     - Store `dse_email_read_ack = 'true'` and `dse_whatsapp_read_ack = 'true'`.
     - Zero out `counts.email` and `counts.whatsapp` in `dse_shell_counts` cache.
  3. In `js/app.js:239-242`, respect `localStorage.getItem('dse_whatsapp_read_ack') === 'true'` by setting `waCount = 0` and adding class `zero`.
  4. In `NotificationCenterController.js:592`, when `openModal()` is invoked, update `#badge-notifications` counter or offer instant 1-click "Mark All as Read".

### Defect 5: New Purchase Recon Save Button Fails to Add Record to Register
- **Root Cause:**
  1. In `PurchaseReconController.js:436`:
     ```javascript
     await window.ReconService.createReconRecord(payload);
     if (window.AppDialogService) window.AppDialogService.toastSuccess('Purchase recon record created.');
     ```
     `AppDialogService.toastSuccess()` invokes `this.showToast()` which calls `this.success(...)` returning a modal Promise. If dismissed or if an unhandled error occurs, the subsequent calls `closeReconEditor()` and `loadPurchaseRecon()` are aborted.
  2. In `PurchaseReconController.js:63`:
     ```javascript
     const pageRes = await window.ReconService.getReconRecordsPage(currentPage, pageSize, q, status);
     reconRecords = pageRes?.rows || [];
     ```
     Spring Data Page responses from the backend return `{ content: [...], totalElements: ... }` rather than `rows`. Because `pageRes.rows` is undefined, `reconRecords` is parsed as `[]` (empty list)!
- **Architectural Solution:**
  1. Update `PurchaseReconController.js:63` to handle all server pagination shapes:
     ```javascript
     reconRecords = pageRes?.rows || pageRes?.content || (Array.isArray(pageRes) ? pageRes : []);
     totalRows = pageRes?.totalRows || pageRes?.totalElements || reconRecords.length;
     ```
  2. Wrap toast notification in a safe try-catch:
     ```javascript
     try {
       if (window.AppDialogService && window.AppDialogService.toastSuccess) {
         window.AppDialogService.toastSuccess('Purchase recon record created.');
       }
     } catch (_) {}
     closeReconEditor();
     await loadPurchaseRecon();
     ```
  3. Ensure `closeReconEditor()` closes the new window modal dialog and immediately triggers fresh register re-render.

### Defect 6: Settings Screen Shows Blank When Opened from Left Sidebar Menu
- **Root Cause:**
  - In `index.html` lines 977-1010, the left sidebar sub-items invoke `selectNav('view-settings-company')`, `selectNav('view-settings-payment')`, `selectNav('view-settings-invoice')`, etc.
  - In `NavigationRouter.js:154`:
    ```javascript
    if (window.ViewLoader && typeof window.ViewLoader.loadView === 'function') {
      await window.ViewLoader.loadView(viewId);
    }
    ```
  - `ViewLoader.loadView()` attempts to fetch `./views/settings-company.html`, which DOES NOT EXIST (all settings sub-sections reside inside the monolithic `views/settings.html`).
  - The fetch returns a 404 error, `targetView` is never mounted, and the screen displays completely blank.
- **Architectural Solution:**
  - In `NavigationRouter.js:153-158`:
    ```javascript
    const isSettingsSub = viewId.startsWith('view-settings-');
    const loadId = isSettingsSub ? 'view-settings' : viewId;
    if (window.ViewLoader && typeof window.ViewLoader.loadView === 'function') {
      await window.ViewLoader.loadView(loadId);
    }
    const domViewId = isSettingsSub ? 'view-settings' : viewId;
    const targetView = document.getElementById(domViewId);
    ```
  - After `view-settings` is active, invoke:
    ```javascript
    if (isSettingsSub) {
      const sec = viewId.replace('view-settings-', '').toUpperCase();
      if (window.SettingsController && window.SettingsController.switchSection) {
        window.SettingsController.switchSection(sec);
      }
    }
    ```
  - In `ViewLoader.js`, register explicit aliases in `VIEW_PATHS`:
    `'view-settings-company': './views/settings.html'`, `'view-settings-payment': './views/settings.html'`, etc.

  2. In `views/purchase-creation.html:305-306`, wire buttons directly to `window.PurchaseController.previewEditorAttachment()` and `window.PurchaseController.removeEditorAttachment()` to match Quotation Editor parity.

## 5. Reactive Reflow Authority on Sidebar Toggle

### Root Cause
- When the user toggles the sidebar (`NavigationRouter.toggleSidebar()`), `aside.app-sidebar` switches between `collapsed` (0px width) and `expanded` (270px width).
- Because `main-content-stage` changes width dynamically, data tables must immediately re-calculate their percentage column widths.
- Currently, `DynamicTableLayoutManager` only listens to container resize via `ResizeObserver`, which can lag or fail to trigger if the container has CSS transitions or overflow constraints.

### Architectural Solution
- In `NavigationRouter.js`, hook `DynamicTableLayoutManager.reflowAllTables()` directly into:
  1. `toggleSidebar()`
  2. `showSidebarDrawer()`
  3. `hideSidebarDrawer()`
  4. Tab switch events in `WorkspaceTabsController`
- Ensure a 50ms debounced relayout pass runs immediately after sidebar animation completes.
